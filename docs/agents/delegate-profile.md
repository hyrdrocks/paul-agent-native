# Delegation profile

Read by `/delegate-tickets` (step 1). Amended by the coordinator when a merge-back reveals a new
baseline, known-noise test, or environment trap.

**Where tickets live is not recorded here** — see `docs/agents/issue-tracker.md`.

- **Remote**: `hyrdrocks/paul-agent-native` — a clean fork of `BuilderIO/agent-native` at core `0.133.3`, created 2026-08-03 for the vault-lease work. **Distinct from `sonhyrd/agent-native`** (28 commits of Cloudflare work, ADRs `0002`–`0005`); this fork deliberately does not build on that one, so its `docs/adr/` is empty and the next free ADR number is `0001`.
- **Branch prefix**: `sss/`
- **Post-merge check**: `pnpm typecheck && pnpm test:fast && pnpm guards`. Do not import the `agent-native` profile's known-failing list, which was measured on a different fork at a different commit.
  - **Setup**: `pnpm install --ignore-scripts`, **not** a bare `pnpm install`. This machine has no C toolchain — `make` and `g++` are both absent (verified 2026-08-03) — so `node-pty`'s gyp build fails, aborts the whole install, leaves root bins unlinked, and every later `prepack` dies with `tsx: not found`. Nothing in a core or dispatch build needs the native binary, so `--ignore-scripts` is sufficient.
  - **Build order matters and `--ignore-scripts` breaks it.** `packages/core` imports `@agent-native/toolkit` subpaths that resolve to toolkit's `dist`, which no longer gets built for you. Build toolkit before core or you get a wall of `TS2307: Cannot find module '@agent-native/toolkit/…'` — a stale-artifact failure wearing the shape of missing code.
  - **Baseline measured at `dcc028cb` (2026-08-03, ticket #14):** `typecheck` clean, `guards` ALL PASS, `test:fast` red for two unrelated reasons — `templates/design` was already **117 tests red**, and *everything else* red only because `--ignore-scripts` leaves `better-sqlite3` with **no native binding**. Fix that with `npx prebuild-install` in `node_modules/better-sqlite3` (not `pnpm rebuild`, which needs the absent C toolchain); after it, `packages/dispatch` is 64 files / 364 tests green. **A wall of red `test:fast` output on a fresh worktree is almost certainly this, not your change** — check the binding before you debug anything else.
  - **Run tests as `env -u CODEX_HOME pnpm test:fast`.** Orca injects `CODEX_HOME` into worker terminals, which makes every Codex config test read the wrong file. Found independently by the #18 and #20 workers: with it unset, `packages/core` goes from 14 red `connect.spec.ts` failures to 745 files all green.
  - **The `templates/design` 117-red figure is not machine-independent.** #20 did not reproduce it — those tests need Playwright browsers that may or may not be installed. Measure the baseline on your machine rather than inheriting this number.
  - **Two more load-flakes measured at the 2026-08-06 integration gate** (both green re-run alone): `packages/dispatch` `src/db/migrations.spec.ts`, and `packages/creative-context` `src/connectors/figma-native.visual.spec.ts`. The latter fails under load with `system Chrome launch failed at /usr/bin/google-chrome-stable: missing shared library` — an environment message that reads like a broken install but disappears in isolation. The full known-flake set is now: `packages/docs` ×2, `packages/dispatch` migrations, `packages/creative-context` figma-native.visual, `templates/factory`, `templates/crm`, `templates/slides`.
  - **`templates/slides` joins the load-flake list** (measured 2026-08-06 by the #7 worker: red in a full sweep, green re-run in isolation). Same 5000 ms timeout shape as the four below. That worker also measured `templates/design` **fully green, 422 files**, on this machine — so treat the 117-red figure above as machine-specific, not a baseline.
  - **Four `test:fast` failures are load-flaky 5000 ms timeouts** (`packages/docs` ×2, `templates/factory`, `templates/crm`) that pass when re-run in isolation, and one (`templates/clips` audio-only-transcription) is deterministic and pre-existing. Re-run a suspected failure alone before calling it a regression.
  - **Rebuild core in the merge worktree before believing a merge-back typecheck failure.** Any change to `packages/core/src/**` typechecks fine on the worker's branch (it rebuilt core) and then fails at merge-back against a stale `packages/core/dist`. Observed on #15: `error TS2561: 'targetTypes' does not exist in type 'AuditQueryFilters'` — a field that was plainly present in core's source. The message reads like the field was never added. Run `node scripts/prebuild-workspace-packages.ts postinstall` in the integration checkout, then re-run. This fires for every cross-package core change, so check it before diagnosing anything else.
  - **A fresh worktree also needs `node scripts/prebuild-workspace-packages.ts postinstall`**, run after `pnpm install --ignore-scripts` AND after the toolkit build. Found 2026-08-04 by the #35 worker. Without it `@agent-native/core` has no `dist`, and roughly **15 template packages fail at once** — a far bigger wall of red than the documented `better-sqlite3` case, and easy to misread as a broken change. Check this before the sqlite binding, not after.
  - **The integration checkout needs the `better-sqlite3` binding too, not just worker worktrees.** Learned 2026-08-05 the expensive way: a post-merge `test:fast` in `/home/orca/work/paul-agent-native` came back with 42 failed files and 374 failed tests, and the merge under test looked like the culprit. It was 3016 `better_sqlite3` errors — the same missing binding documented above for fresh worktrees. The merged code's own suites (`vault.spec.ts` 72/72, `connect.spec.ts` 79/79) were green throughout. Fix it once in the pnpm store: `npx --yes prebuild-install` inside `node_modules/.pnpm/better-sqlite3@<version>/node_modules/better-sqlite3`. **Do this before trusting any merge-back gate**, because here the failure does not look like an environment problem — it looks like the merge broke the workspace.
  - **Never run the integration gate while workers are running their own sweeps.** `pnpm test:fast` sizes each package's vitest pool from total cores and knows nothing about sibling runs. Two workers plus one gate on this 8-core host drove load average to 45.79; the gate was SIGTERM'd mid-run with zero assertion failures, and both workers' own suites failed for the same reason. A killed run writes no `EXIT=` line, so any wait-loop polling for one hangs. Serialize: let workers finish, stop them once their work is committed, then gate alone. With the box to itself the same sweep passed `packages/core` 749/749.
  - **A merge-back can fail with `error: Unable to write index` while workers are running.** Seen 2026-08-06 merging #9 while a peer worker ran `pnpm guards` + `test:fast` in its own worktree. It presents as `Automatic merge failed; fix conflicts`, but `git status` then reports no unmerged paths and nothing staged — a transient `.git/index.lock` under load, not a real conflict. `git merge --abort` and retry; it succeeded immediately. Do not start hand-resolving a conflict that is not there.
- **Dispatch traps in the Orca CLI itself** (measured 2026-08-06 dispatching #26). `terminal create` takes **`--worktree path:<abs>`**, not `--cwd`, and `orchestration dispatch` takes **`--to <handle>`**, not `--terminal`. Both matter more than a typo normally would: an unknown flag on `terminal create` still returns `ok: true` and still creates a terminal in the right directory — it just silently drops `--command`, so the pane comes up as a **bare shell with no agent in it**. That is indistinguishable from a worker that died on startup, and `terminal wait --for tui-idle` is satisfied by it. Always follow the wait with a `terminal read` and require a rendered agent frame (the Claude Code banner and the `bypass permissions` footer) before dispatching; close and recreate otherwise. Note also that `terminal read`'s JSON nests under `result.terminal.tail` — the key is `tail`, not `lines`.
- **The Orca CLI's terminal verbs and its orchestration verbs disagree about the same flag.** `orchestration dispatch` takes **`--to <handle>`**; `terminal read` and `terminal wait` reject `--to` and take **`--terminal <handle>`**, and `terminal wait`'s timeout is **`--timeout-ms`**, not `--timeout`. Measured 2026-08-07 dispatching wave A of the close-out. The failure is safe here — an unknown flag on `terminal read` returns `ok: false` with a `validFlags` list, so it is loud — but it lands on the *verification* step that exists to catch the silent `terminal create` failure documented above, so a wait/read pair that both quietly error looks exactly like a worker that never started. Check `ok` on every terminal call and require a rendered agent frame before dispatching, never the absence of an error.
- **A `git merge` that prints `Unable to write index` leaves a partial merge that looks finished, and the gate will confirm it.** Hit 2026-08-07 merging R5. The merge failed, but `git status` then said *"All conflicts fixed but you are still merging"* — which it says whenever no conflict markers remain, **including when the index was never populated** — so `git commit --no-edit` produced a merge commit that deleted 1912 lines and every new file the branch added. `pnpm guards` and `pnpm typecheck` then both passed **because the code was not there**, which is the whole trap: a green gate measured against an empty change is indistinguishable from a green gate measured against the work. **After every merge-back, before gating, run `git diff --stat <branch>` against the merged tree and require it to be empty.** Recovery is a `reset --hard` to the pre-merge commit and a clean re-merge — the integration branch is unpushed, so nothing is lost. Never read a `git status` prose line as confirmation that a failed command succeeded.
- **A monitored background test run can be killed and still write a plausible-looking failure.** Same session: `packages/core test: Failed` with no test output at all above it, because the sweep was killed mid-run rather than having failed. Before diagnosing a package failure, check that the package actually emitted `Test Files`/`Tests` summary lines; a bare `Failed` with no counts is a truncated run, not a result.
- **`orchestration dispatch` needs a task, and the CLI's task verbs are not the ones you will guess.** Measured 2026-08-07 dispatching #15. There is **no `task-get`** — it is `task-list --run <run>`, and you filter client-side. `task-create` takes **`--task-title`** and **`--spec`** (the brief text itself, not a file path); `--title` and `--brief-file` are both rejected. `dispatch` needs `--run` and `--task` alongside `--to`. This matters because of what it does to a *watch*: a monitor that calls a nonexistent subcommand and falls back with `|| echo unknown` polls forever and can never fire — the failure is invisible because the fallback value is indistinguishable from a live status. It is the same silent-coercion shape this repo is organised against, and it cost #15 a two-hour blind spot. Any monitor over the Orca CLI must treat a CLI error as an **event to report**, never as a status to substitute.
- **A worker's approval ask can time out, and it then finishes green with work unpushed.** Seen 2026-08-07 on #15: the brief said "ask before pushing to `paul-dispatch-app`", the worker asked twice, both asks timed out, and it reported `succeeded` with its App Repo commit sitting local. `worker_done` is not evidence that everything the brief asked for was delivered — read the report's App Repo section and check `git -C <app-repo> status -sb` for `ahead N` before closing the ticket. Answering the ask through `terminal send` also does not help once the worker has already given up on it.
- **`gh` fails on Projects-classic GraphQL deprecation for plain `issue view` and `pr edit`.** Measured 2026-08-07. `gh issue view <n> --repo <r> --comments` returns *only* the deprecation error and no issue body; `gh pr edit --title/--body` fails the same way while still having pushed nothing. Workarounds: `gh issue view <n> --json number,title,body,state` for reads, and `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> --input <json>` for PR metadata. Both are silent-failure adjacent — `gh pr edit` exits non-zero but a `git push` in the same script has already succeeded, so the branch advances while the PR still describes the previous rung.
- **Every Orca-created worktree needs two corrections before launch, every time.** Orca applies its own `sonhyrd/` branch prefix, and bases the worktree on `origin/main` rather than the local integration `main`. Both fired again on #26 (`sonhyrd/fix-nested-chunk-postbuild` at `31e2be3a`). Fix in this order, before any commit: `git -C <wt> branch -m sss/<name>` then `git -C <wt> reset --hard $(git -C <integration> rev-parse main)`. Skipping the second silently gives the worker a tree missing every merged ticket, and its brief's stated base commit will be wrong.
- **An Orca runtime restart fences an in-flight dispatch, and the worker cannot report.** Seen 2026-08-06 on #26. The runtime came back with a new `runtimeId`, every existing terminal handle went `terminal_handle_stale`, and the worker's pty survived under a **new** handle — so the agent kept working and finished green, but `worker_done` was rejected first with `The caller is not the Dispatch pane` (preamble handle) and then `The Dispatch process incarnation changed` (`$ORCA_TERMINAL_HANDLE`). The task sits at `dispatched` forever and a status-only watch will never fire. Recovery: re-find the terminal by `worktreePath` in `terminal list`, read the branch for its commit, and take the report from the worker's report file — `orca orchestration check --peek` still works, and a well-briefed worker escalates the report path through it. **Brief every worker to write its report to a file**, not only into `worker_done`; that is the only channel that survives this.
- **The "three pre-existing `packages/core` failures" baseline is stale — two of the three now pass, and the surviving one is a timeout, not an assertion.** Originally confirmed 2026-08-06 by the #29 worker with a verified-clean revert check: `src/deploy/build.spec.ts > generateWorkerEntry > strips mounted /api prefixes…`, `scripts/materialize-source-corpus.test.mjs`, and `src/cli/create-e2e.spec.ts`. Re-measured 2026-08-07 by R5 and again by R6: `build.spec.ts` **passes** in every run, `materialize-source-corpus` **passes** 10/10, and `templates/clips` audio-only-transcription — recorded here as deterministic — **passes** too. Only `create-e2e.spec.ts > overrides toolkit for standalone installs` still fails, as a **180 s wall-clock timeout on a test that runs a full `pnpm install`**, with the cap set inline in the spec so `--testTimeout` cannot lift it. That is load-dependent, not deterministic, which is why the original revert check and later runs disagree. Two of the three are invisible in `pnpm test:fast`, which excludes `create-e2e.spec.ts` and `*.integration.spec.ts` — so a standalone `packages/core` run still shows failures the gate does not, and that difference is the runner's exclusion list, not a regression. **Do not hand a worker this list as settled fact**: brief it to re-measure and say what it actually saw, the way R6 did when it declined to claim the install timeout was someone else's without proving it.
- **A merge that adds a dependency needs `pnpm install --ignore-scripts` in the integration checkout BEFORE the gate.** Seen 2026-08-06 merging R2 (#13), which added `@cfworker/json-schema` to `packages/core`. Both `pnpm typecheck` and `guard:eject-manifests` failed with `Cannot find package '@cfworker/json-schema'` — and the package is plainly declared in `packages/core/package.json` and present 15 times in `pnpm-lock.yaml`, so the message reads exactly like the worker forgot to declare it. It is a stale `node_modules` in the merge checkout. Same family as the stale-`dist` trap above: check the lockfile before doubting the branch, then install, rebuild, and re-gate. Instruct workers to flag any new dependency prominently in their report, because the failure surfaces two steps later in someone else's checkout.
- **`packages/core` `src/server/framework-request-handler.dispatch.spec.ts` is a load flake**, measured 2026-08-06 at the R3 gate: red in the full sweep on `cold-isolate dispatch on Cloudflare Workers > does not let the app's catch-all answer a gated path mid-init`, green alone (11/11). It asserts init *timing* through #9's poll-and-wait memo, so it is inherently sensitive to a loaded box. Worth knowing because it fails with a Cloudflare cold-isolate name, which reads like a real regression to anyone working on Workers — and because the deterministic `build.spec.ts` failure did **not** appear in that same sweep, so which core spec is red varies run to run. Re-run alone before concluding anything about either.
- **Commit policy**: conventional commit, **no issue-closing trailers**. Origin is a fork of BuilderIO and the tickets live in a third repo, so `closes #N` would point at an unrelated upstream issue. The coordinator closes tickets explicitly. Never add `Co-Authored-By` or agent attribution.
- **Worker constraints**:
  - **Pre-mode is already entered** (`.changeset/pre.json`, tag `paul`; core is `0.134.0-paul.0`). Add a changeset for your work, but do **not** run `changeset:version` and do **not** run `changeset pre exit` — versioning happens once per vendor cycle, in `paul-dispatch-app`'s #17 flow.
- **`.changeset/pre.json` is repo-global — never create it on a ticket branch.** `changeset pre enter paul` pins `initialVersions` for all 21 packages, so every branch that runs it produces an identical file and every merge-back after the first conflicts. Ticket #18 owns entering pre mode, once, after the rest have merged. Individual tickets ship a plain changeset only.
  - **Changeset required** for any source change under `packages/core` or `packages/dispatch` (`pnpm changeset:add`). Never hand-bump a package version. The changeset does **not** publish — the `@agent-native` npm scope is owned by `steve8708` and this fork cannot publish to it. It exists to version the fork and write its CHANGELOG.
  - The version minted must be one **upstream will never issue** — `0.134.0-paul.N`, not a reused `0.133.3` — so a fork build identifies itself in `pnpm list` and in stack traces. See `paul-dispatch-app`'s `docs/adr/0001`.
  - Read `CLAUDE.md` first, and the matching skill in `.agents/skills/` before changing that area; `secrets` is load-bearing for the vault work.
  - Migrations are additive only; never drop, rename, or truncate.
  - Never hardcode API keys, tokens, webhook URLs, or signing secrets — in source, tests, fixtures, or issue comments.
  - **Never `git stash`** — the stash is shared across worktrees and would steal another worker's WIP.
  - **Measure any baseline against `git merge-base main HEAD`**, never `HEAD` and never `main..HEAD`.
  - **Stay on your own branch.** The coordinator owns merge-back.
